# Aider — Base Behavior Rules

## Behavior

- Read files before modifying them. Use `/add <file>` to load context.
- Use `/edit` for targeted changes to specific files.
- Use `/ask` to understand code before changing it.
- Enable diff mode (`show-diffs = true`) for surgical edits — review diffs before confirming.
- Run tests after each change; do not proceed if tests fail.

## Workflow

- **One change per commit.** Atomic commits using Conventional Commits format.
- **TDD:** Write failing tests before implementation. Red → Green → Refactor.
- **Keep context lean:** `/add` only the files needed for the current task. `/drop` files when done.
- Use `/ask` to clarify requirements before making significant structural changes.
- **Worktrees:** work in `git worktree add {{WORKTREE_DIR}}/<branch> -b <branch>`, created from the main checkout (the root is `worktree_dir:` in `.standards.yml`); never work in the root checkout, never nest worktrees. One task = one branch = one worktree = one PR; run the project's full local gate (`make ci`, which must mirror CI) before pushing, and `git worktree remove {{WORKTREE_DIR}}/<branch>` after the merge.

## Constraints

- Do not add generated files, lock files, or vendored dependencies to the chat context.
- Do not include secrets or credentials — check `.gitignore` before `/add`-ing config files.
- Before changing a public API or function signature, check all callers first.
- Conventional Commits are required: `type(scope): subject`.
- If sync-standards reports customized files, pending updates are in `.standards-pending/`. Follow the `merge-standards` runbook in the Skills section below, or see `.standards/docs/reference/merge-standards-prompt.md`.

## Known Traps

Project-specific pitfalls that have already cost a debugging session, kept as a table whose rows carry the issue that documented the trap and the date it was recorded, so a reader can judge whether it is still live. Add a row whenever a bug's root cause was "the agent did not know this"; delete the row when the trap is engineered away and say so in the issue.

The table lives in the PROJECT-SPECIFIC section at the end of this file (`setup.sh` seeds one there with an example row). Everything above that marker is regenerated by `sync-standards`, so a row added here would be staged for a manual merge instead of kept.
